# Studio 313 — руководство по первичной генерации страниц

Этот документ — рабочий контракт для создания новых страниц Studio 313. Он дополняет [`websiteDesignIdea.md`](./websiteDesignIdea.md) и фиксирует практические правила, по которым краткий пользовательский бриф превращается в готовую Nuxt-страницу.

Главный принцип:

> Сайт — это цифровой production-интерфейс и монтажная линия Studio 313, а не набор типовых блоков лендинга.

## 1. Как поставить задачу

Для начала достаточно трёх пунктов:

```text
Страница:
/route и название страницы

Контент:
Тексты, списки, услуги, цены, факты, CTA и другие известные данные

Видение:
Желаемое настроение, композиция, референс или ключевая визуальная идея
```

Расширенный шаблон, если детали уже известны:

```text
Страница:

Цель страницы:

Целевая аудитория:

Контент:

Главное действие пользователя:

Вторичные действия:

Видение и настроение:

Предпочтительный тип страницы:
PageFullscreen / PageLongScreen / гибрид / на усмотрение

Изображения или видео:

Ограничения и обязательные элементы:
```

Если заполнены только первые три пункта, остальные решения принимаются самостоятельно на основе этого документа, текущего проекта и контекста страницы.

## 2. Приоритеты при проектировании

Решения принимаются в следующем порядке:

1. Прямые требования пользователя для конкретной страницы.
2. Фактический предоставленный контент и бизнес-ограничения.
3. Инструкции проекта из корневого `AGENTS.md`.
4. Правила этого документа.
5. Общая концепция из `websiteDesignIdea.md`.
6. Уже существующие компоненты, паттерны и дизайн-токены проекта.

Если пользователь не указал деталь, нужно сделать разумное дизайнерское предположение и продолжить работу. Уточнение требуется только тогда, когда выбор существенно меняет бизнес-смысл, цену, юридически значимое утверждение или основное пользовательское действие.

Нельзя придумывать как факт:

- неподтверждённые цены;
- характеристики оборудования;
- количество камер, людей или площадок;
- сроки производства;
- гарантии результата;
- названия партнёров и площадок;
- адреса, контакты и юридические условия.

Если точных данных нет, используются нейтральные формулировки: «от», «по запросу», «зависит от задачи», «согласованные площадки».

## 3. Дизайн-ДНК Studio 313

Страница должна ощущаться как часть единой production-системы.

Образ бренда:

- премиальный;
- кинематографичный;
- технологичный;
- редакционный;
- уверенный;
- минималистичный;
- связанный с реальным производством контента.

Визуальный язык:

- крупная editorial-типографика;
- асимметричные композиции;
- выразительные фотографии и видео;
- монтажные линии и waveform;
- REC, CAM, ON AIR и осмысленные production-метаданные;
- тонкие рамки, координаты, номера и технические подписи;
- большое количество негативного пространства;
- синий цвет как функциональный акцент;
- контраст светлых и тёмных сцен.

Страница не должна выглядеть как:

- SaaS-лендинг;
- шаблон креативного агентства;
- UI kit;
- однообразная сетка карточек;
- набор стеклянных панелей;
- коллекция градиентных декоративных пятен;
- интерфейс, перегруженный вымышленными техническими показателями.

Дорогой вид создаётся композицией, масштабом, ритмом, фотографией, типографикой и аккуратным motion — не количеством эффектов.

## 4. Цвет и типографика

Использовать существующие токены Tailwind из `app/assets/css/app.css`:

```text
accent       #0069FE
accent-600   #0051C6
accent-700   #004FC4
accent-800   #003F9D
ink          #07101F
copy         #1B2433
page         #F7F9FC
white        #FFFFFF
```

Основные правила:

- `bg-ink` и `bg-page` формируют главные плоскости.
- `text-accent` показывает активность, состояние записи, цену или CTA.
- Полностью синий экран используется редко — преимущественно для сильного финального CTA.
- Не создавать новые оттенки без композиционной необходимости.
- Сохранять достаточный контраст текста и интерактивных элементов.

Шрифты:

- `font-display` — крупные заголовки, номера, цены, навигация и важные заявления.
- `font-body` — описания, метаданные, формы и вспомогательный интерфейс.
- Один `h1` на страницу.
- Остальная структура должна иметь последовательную иерархию `h2` → `h3` → `h4`.
- Uppercase используется выборочно, преимущественно для display-текста и коротких labels.

## 5. Выбор типа страницы

### PageFullscreen

Используется для нескольких самостоятельных narrative-сцен:

- большие услуги;
- этапы производства;
- презентация пространства;
- оборудование;
- кейсы с сильным медиа;
- короткая брендовая история.

Каждый прямой дочерний экран должен:

- иметь `data-page-section`;
- иметь стабильный `id`;
- занимать минимум высоту контейнера;
- передавать законченную мысль;
- отличаться композицией, но оставаться частью общего ритма.

`PageFullscreen` отвечает только за:

- fullscreen-scroller;
- scroll snapping;
- camera frame;
- определение активной внутренней секции;
- событие `active-change`.

`PageFullscreen` не должен импортировать или рендерить `SectionTimeline`.

### PageLongScreen

Используется для контентных и индексируемых разделов:

- длинный прайс;
- FAQ;
- статьи;
- контакты;
- подробное описание услуги;
- условия работы;
- длинные списки и каталоги.

Длинная страница должна иметь выраженный редакционный ритм: intro, смысловые группы, различимые заголовки, достаточные интервалы и сильный финальный CTA.

### Гибрид

Предпочтительный вариант, когда странице нужны одновременно брендовый опыт и подробный контент:

```text
PageFullscreen
├── scene 01
├── scene 02
└── scene 03

PageLongScreen
├── подробности
├── прайс или каталог
└── CTA
```

Fullscreen-сцены создают желание и понимание продукта. Длинная часть отвечает на рациональные вопросы, поддерживает SEO и конверсию.

## 6. SectionTimeline

`SectionTimeline` всегда подключается непосредственно в шаблоне страницы или её page-widget, но не внутри `PageFullscreen`.

Правила:

- В timeline входят все значимые секции страницы, включая длинные.
- Labels должны быть короткими и понятными без контекста.
- Каждая секция получает собственный waveform.
- Активный индекс синхронизируется с фактической видимой секцией.
- Клик прокручивает к соответствующему `id`.
- `prefers-reduced-motion` отключает плавную прокрутку.
- Если страница длиннее одного fullscreen-контейнера, timeline обычно используется в режиме `fixed`.
- На мобильном фиксированный timeline располагается над нижним navigation dock.
- На десктопе он учитывает раскрытый или свёрнутый sidebar.

Для зарезервированного места используется переменная на корне страницы:

```html
<div class="page-name bg-ink [--page-bottom-inset:3.75rem]">
```

Для общей логики активной полноэкранной и длинной секции использовать feature-composable `useSectionNavigation` либо развивать его без привязки к конкретной entity.

## 7. Архитектура Feature-Sliced

Route-файл страницы — оркестратор, а не место хранения всего интерфейса.

Базовая структура:

```text
app/
├── pages/
│   └── page-name.vue
├── entities/
│   └── entity-name/
│       ├── config/
│       └── model/
├── features/
│   └── user-action/
│       └── model/
├── widgets/
│   └── page-block/
│       └── ui/
└── shared/
    └── ui/
```

### Pages

Содержат:

- SEO;
- сборку виджетов;
- route-level состояние;
- соединение независимых блоков страницы;
- `SectionTimeline`, если он относится ко всей странице.

Желательный объём route-файла — около 50–120 строк. Это ориентир, а не искусственный лимит.

### Entities

Содержат бизнес-сущности:

- типы;
- статический контент;
- конфигурацию;
- небольшие UI-представления сущности, если они используются в разных виджетах.

Контент повторяемых секций не должен находиться большим массивом внутри route-файла.

### Features

Содержат пользовательское поведение:

- навигацию по секциям;
- фильтрацию;
- выбор категории;
- управление проигрыванием;
- бронирование;
- отправку формы.

Feature не должна зависеть от конкретной entity, если её поведение является общим.

### Widgets

Содержат крупные законченные блоки страницы:

- fullscreen showcase;
- прайс-лист;
- галерею кейсов;
- контактный блок;
- каталог оборудования.

Widget может собирать shared-компоненты, features и entities.

### Shared UI

Содержит универсальные примитивы без знания конкретного бизнеса:

- `PageFullscreen`;
- `PageLongScreen`;
- `PageFullscreenContent`;
- `SectionTimeline`;
- `CameraFrame`;
- общие кнопки и иконки.

## 8. Когда создавать компонент

Компонент оправдан, если выполняется хотя бы одно условие:

- блок повторяется;
- у блока есть самостоятельная ответственность;
- блок имеет собственные props/emits;
- блок скрывает сложную адаптивную разметку;
- блок содержит отдельное поведение;
- блок вероятно будет переиспользован.

Не нужно создавать компоненты только ради уменьшения количества HTML для:

- одного заголовка;
- единственного декоративного элемента;
- простого label;
- одного CTA;
- уникального footer;
- div-контейнера без поведения.

Если дизайн повторяющихся секций различается, использовать явный `variant`:

```ts
variant: 'space' | 'production' | 'distribution'
```

Не привязывать смысловое оформление к `index === 1`, если вариант является частью бизнес-конфигурации.

## 9. Tailwind — обязательная система стилей

Разметка, размеры, сетки, отступы, цвета, типографика, состояния и адаптивность реализуются Tailwind-классами.

Разрешено:

- стандартные utilities;
- responsive variants;
- arbitrary values;
- arbitrary properties;
- arbitrary selectors;
- существующие theme-токены;
- корневой hook-класс страницы или компонента, даже если он не имеет CSS;
- отдельный CSS только для действительно сложной анимации, которую неразумно выразить utilities.

Не разрешено для обычной стилизации:

- большие `<style scoped>` блоки;
- BEM-таблицы стилей страницы;
- дублирование theme-токенов;
- `@apply` ради маскировки длинных utility-списков;
- создание глобального класса для уникальной композиции одной страницы.

Если набор разметки и utilities повторяется, следует выделить компонент, а не создавать CSS-класс-комбайн.

## 10. Изображения и медиа

- Использовать `NuxtImg` для изображений.
- Первый критичный hero-кадр может иметь `preload` и eager loading.
- Остальные изображения загружаются лениво.
- Всегда задавать содержательный `alt`, если изображение несёт смысл.
- Для декоративного изображения использовать пустой `alt`.
- Указывать подходящий `sizes`.
- Сначала проверять доступные материалы в `public/media`.
- Не использовать случайную фотографию только для заполнения пространства.
- Не запускать image generation без явной необходимости или соответствующего запроса.

Photography/video должны быть частью композиции, а не фоном под стандартный текстовый блок.

## 11. Адаптивность

Desktop breakpoint проекта: `desktop` (`67.5rem`).

На десктопе учитывать, что часть viewport занимает sidebar. Композиция должна сохраняться не только на широком мониторе, но и в оставшейся после sidebar области.

Мобильная версия:

- превращает горизонтальный или fullscreen-опыт в понятный вертикальный narrative;
- не зависит от hover;
- сокращает второстепенные метаданные;
- сохраняет главное действие доступным;
- учитывает `--mobile-dock-height`;
- не прячет контент под `SectionTimeline`;
- не пытается уместить desktop-композицию простым уменьшением масштаба;
- избегает тяжёлого parallax и лишних декоративных эффектов.

Использовать `dvh`, проектные safe-area переменные и существующие responsive utilities.

## 12. Motion

Motion должен напоминать монтаж и работу студийного оборудования:

- переключение кадра;
- появление REC;
- waveform activity;
- небольшой stagger;
- контролируемый scale изображения;
- аккуратный scrub по timeline.

Не использовать motion только ради демонстрации анимации.

Обязательно:

- уважать `prefers-reduced-motion`;
- не блокировать навигацию анимацией;
- сохранять корректное состояние после быстрого scroll или клика;
- избегать постоянных ресурсоёмких эффектов.

## 13. Доступность

- Один осмысленный `h1`.
- Последовательная иерархия заголовков.
- Интерактивные элементы должны быть `button` или `a`, а не кликабельными `div`.
- У кнопок должна быть доступная подпись.
- Декоративные иконки получают `aria-hidden="true"`.
- Навигация получает `aria-label`.
- Активная секция timeline получает `aria-current`.
- Контент должен быть доступен с клавиатуры.
- Focus state нельзя удалять без полноценной замены.
- Цвет не должен быть единственным способом передать состояние.
- Текст поверх изображения должен иметь стабильную контрастную подложку.

## 14. Контент и конверсия

Каждая страница должна быстро отвечать на вопросы:

1. Где я нахожусь?
2. Что предлагает Studio 313?
3. Для кого это?
4. Что входит в результат?
5. Что мне делать дальше?

У страницы должно быть одно главное действие. Вторичные CTA не должны спорить с ним по визуальному весу.

Для услуги желательно предусмотреть:

- ясный hero;
- состав услуги;
- процесс или сценарий работы;
- доказательство результата;
- цену или принцип расчёта;
- связанные услуги;
- финальный CTA.

Не обязательно показывать все эти элементы одинаковыми блоками. Они должны быть встроены в narrative страницы.

## 15. SEO

Каждая route-страница получает `useSeoMeta`:

```ts
useSeoMeta({
  title: 'Название — Studio 313',
  description: 'Конкретное описание содержания и пользы страницы.',
  ogTitle: 'Название — Studio 313',
  ogDescription: 'Краткое описание для публикации.',
  ogImage: 'https://studio313.ru/media/static/313.jpg',
})
```

SEO-текст не должен превращать страницу в полотно общих фраз. Индексируемый контент распределяется по осмысленным заголовкам, описаниям, спискам и FAQ.

## 16. Рабочий процесс генерации страницы

### Шаг 1. Исследование

Перед реализацией нужно:

- прочитать `AGENTS.md`;
- изучить пользовательский бриф;
- проверить `websiteDesignIdea.md`;
- найти существующую route-заглушку;
- изучить близкие страницы и shared UI;
- проверить доступные медиа;
- определить затрагиваемые сущности, features и widgets.

### Шаг 2. Карта страницы

До кода определить:

- тип страницы;
- список секций;
- порядок narrative;
- главное действие;
- timeline;
- мобильную трансформацию;
- повторяемые бизнес-сущности;
- границы компонентов.

### Шаг 3. Реализация

- Сначала типы и конфигурация контента.
- Затем повторяемые entity UI или widgets.
- После этого поведение features.
- В конце route-level композиция и SEO.
- Не смешивать content-массивы, IntersectionObserver и сотни строк шаблона в одном page-файле.

### Шаг 4. Проверка

Обязательные проверки:

```powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
git diff --check
```

Также проверить по коду:

- отсутствие случайного `<style scoped>` в новой странице;
- отсутствие дублированного контента;
- корректность ссылок и `id`;
- соответствие timeline секциям;
- наличие SEO;
- alt и aria-атрибуты;
- отсутствие скрытого за dock/timeline контента.

Не запускать браузер, screenshots, visual regression или dev server только ради визуального просмотра. Интерфейс проверяет пользователь вручную, если он отдельно не попросил иначе.

## 17. Definition of Done

Страница считается готовой, когда:

- реализован весь предоставленный контент;
- дизайн соответствует Studio 313 и не выглядит шаблонным;
- выбрана обоснованная fullscreen/long/hybrid структура;
- `SectionTimeline` находится на уровне страницы;
- desktop и mobile имеют осмысленные композиции;
- стили реализованы Tailwind utilities;
- повторяемые блоки декомпозированы без атомарной раздробленности;
- page-файл остаётся оркестратором;
- данные и типы находятся в подходящем слое;
- пользовательское поведение вынесено в feature при наличии самостоятельной логики;
- есть SEO, доступные подписи и корректная семантика;
- lint, typecheck, build и diff-check проходят;
- в финальном отчёте перечислены основные изменения и результаты проверок.

## 18. Пример короткого запроса

```text
Используй tasks/page-generation-guide.md.

Страница:
/equipment — Оборудование

Контент:
Камеры, звук, свет, grip и streaming. В каждой категории 4–8 позиций с названием и характеристиками.

Видение:
Production desk. Большая единица оборудования в фокусе, категории переключаются по внутреннему timeline. После fullscreen-каталога нужен длинный список всей техники.
```

Такого запроса достаточно, чтобы самостоятельно определить структуру, компоненты, адаптивность и способ реализации страницы в рамках общей системы Studio 313.
